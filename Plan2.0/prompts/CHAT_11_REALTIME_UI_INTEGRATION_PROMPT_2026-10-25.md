# Chat 11 — Real-Time STM32 Telemetry to Existing UI

**Project:** Embedded Runtime Resilience — Plan 2.0  
**Repository:** https://github.com/SujitSaiY2007/embedded-runtime-resilience  
**Branch:** `main` only  
**Target:** ST NUCLEO-L476RG (STM32L476RG) + BME280 over I2C  
**IDE:** STM32CubeIDE 2.2.0  
**Prerequisite:** Read the Chat 10 final hardware validation report and current handoff first.

## Mission

Integrate real telemetry from the physical STM32 firmware into the existing UI and Python bridge with an explicit distinction between live hardware values and simulated/reference-demo values. Do not redesign or replace the existing UI. Preserve existing routes, styling, interactions, tests and simulation functionality.

## Mandatory safety and preservation rules

1. Inspect live GitHub `main`, current state, handoff, existing UI files, Python bridge, UI contract tests, and `Plan2.0/firmware/bme280_policy_integration/main.c` before edits.
2. Use `main` only. Do not create, switch, rename or delete branches.
3. Preserve `reference/include/ref_runtime.h`, `reference/src/ref_runtime.c`, frozen 400-execution evidence, Gates A–E, historical reports, manuscript, firmware backups and saved screenshots.
4. Do not flash firmware or change hardware without first explaining why, reviewing exact source/build implications, producing a clean build, and obtaining explicit user approval.
5. Do not claim serial/VCP support merely because the ST-LINK exposes a VCP interface. Verify the physical USB connector, Windows device enumeration/COM port, firmware UART/USB configuration, baud rate if applicable, and actual transmitted bytes.
6. Never present simulated/reference data as physical hardware data. Include an explicit source/status marker in UI state and telemetry messages.
7. Do not invent timestamps, sequence numbers, runtime fields, measurements or message formats. Add fields only when implemented and verified.
8. Preserve a working rollback path and keep changes small and auditable.

## Stage 1 — Audit and interface decision

- Read the Chat 10 report and trial ledger. Respect any outstanding hardware evidence limitations.
- Inspect the existing UI, Python HTTP bridge and tests.
- Inspect the target firmware's current transport setup. Current source exposes debugger-visible variables; it does not by itself prove any serial telemetry is transmitted.
- Verify whether the NUCLEO-L476RG/ST-LINK VCP route is usable with the actual firmware and the user's available USB cable/port. Do not ask for new purchases.
- Choose a feasible transport (likely existing ST-LINK VCP + MCU UART only if both wiring/firmware path and actual output are verified; otherwise document the minimal necessary adapter/firmware work). Do not assume that the ST-LINK VCP automatically transports arbitrary MCU UART output.
- Present source files to change, risks, message schema and acceptance criteria before any hardware-affecting work.

## Stage 2 — Define truthful telemetry

Design a small, versioned, newline-delimited JSON schema only if the chosen transport supports it. Candidate fields, when actually implemented, include:
- schema/version and source = `hardware`;
- sensor address and chip ID;
- baseline-read status;
- fault attempted and NACK observed;
- policy variant/action/reason when observed in firmware;
- recovery attempted/result;
- fresh post-recovery read status and ID;
- runtime release result;
- terminal state/report code.

Add a monotonic sequence number or timestamp only if firmware can generate it and its semantics are documented. Define parsing errors, disconnect behavior, stale-data handling and message validation. Keep simulated scenarios on their existing path with a distinct `source=simulation` label.

## Stage 3 — Implement the smallest integration

- Keep the current UI layout and workflows intact.
- Add an explicit live-hardware connection/status indicator, last-message time only if actually measured, and telemetry values sourced solely from received firmware messages.
- Use a separate adapter/endpoint or source discriminator so live hardware events cannot be confused with virtual-system results.
- Validate incoming fields and reject malformed/unknown schemas safely.
- Never fabricate sensor data or a recovery success state when no message arrives.
- Keep host UI tests deterministic; use recorded sample frames for parser tests and label fixtures as fixtures/simulation, not live hardware.

## Stage 4 — Verification

1. Run existing UI contract tests and applicable software tests; report actual commands and results.
2. Unit-test telemetry parsing with valid, malformed, incomplete, stale and disconnect cases.
3. Verify the real transport separately: show actual firmware-generated bytes and the host receive log.
4. End-to-end acceptance: trigger an approved controlled event on the physical board, capture the firmware's actual telemetry, confirm the Python bridge receives and validates it, confirm the UI updates, and compare displayed fields against the debugger/hardware result for the same event.
5. If firmware changes are needed, stop before flashing; present the clean-build result, exact diff and risk, then request explicit user approval.
6. Document limitations, reproduction steps, rollback and troubleshooting.

## Required outputs

- Minimal reviewed firmware transport change only if necessary and approved.
- Host-side telemetry adapter/parser and tests.
- UI changes that preserve existing behavior and distinguish hardware from simulation.
- A Chat 11 integration report with changed files, test commands/results, raw message example, transport verification, end-to-end evidence, limitations and commit SHA.
- Updated current state and handoff on `main`.

## Acceptance criteria

- The host receives real bytes emitted by the target firmware; no simulated data is substituted.
- The UI clearly identifies the data source as physical hardware.
- A controlled event's displayed sensor/fault/recovery fields agree with the same trial's hardware evidence.
- Existing simulation path and UI contract tests remain intact.
- Any unimplemented fields are visibly absent/unknown, not guessed.
- Protected research artifacts remain unchanged.

## First action

Perform Stage 1 read-only audit. Do not edit the UI or flash firmware as the first action. Report the verified communication options and proposed minimal telemetry contract before implementation.
