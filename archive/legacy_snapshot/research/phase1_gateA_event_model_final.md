# Phase 1E.1 — Gate A Final Semantic Contract

**Gate:** A — Exact Event Model and Dependency Semantics  
**Phase:** 1E.1 — Experimental Design / Formalization Foundation  
**Status:** Gate A complete at the semantic-design level; implementation remains deferred until Gates B–E.  
**Date:** 2026-09-03

## 1. Purpose and acceptance boundary

Gate A defines the smallest internally consistent event/dependency semantics needed to reason about selective quarantine and preservation of queued work.

This document supersedes the *design-baseline* status of `research/phase1_event_model.md` for subsequent gates. The original document is retained; it is not deleted because it records the earlier design reasoning.

Gate A is accepted only for the semantic contract. It does not freeze the numerical workload matrix, exact fault taxonomy, recovery-history size, recovery-action policy, or physical fault-injection method. Those belong to later gates.

## 2. Design principles

The reference model is a bounded cooperative/event-driven system. Events are discrete work items with explicit identity, service ownership, resource association, criticality, and dependency metadata.

Three dependency classes are fundamental:

1. **INDEPENDENT** — execution does not require completion or validity established by the referenced event.
2. **ORDERED** — execution requires a predecessor to reach a declared acceptable terminal condition before the successor may execute.
3. **COUPLED/TRANSACTIONAL** — events share a logical transaction, atomic service operation, or state whose validity is jointly affected; a member cannot safely proceed by treating another member as merely delayed.

Peripheral equality is never sufficient to infer dependency. Two events using the same peripheral can be independent, ordered, or coupled depending on transaction and state semantics.

## 3. Exact event identity

Each active event has a bounded identity that is unique for the lifetime of that event within the active event domain.

The semantic identity is:

`EventRef = {slot_id, generation}`

where:

- `slot_id` identifies one of the fixed event-record slots;
- `generation` distinguishes reuse of a slot after the previous event has reached terminal state.

A generation value may wrap only after the implementation guarantees that no outstanding fault/dependency reference can still refer to the older generation. The reference implementation must not rely on an ambiguous recycled identifier.

`transaction_id` is separate from `EventRef`. It is present only when the event belongs to a transaction whose identity must be shared by multiple event records. Transaction identity is bounded and is not a heap object.

An event reference remains valid while the event is QUEUED, ELIGIBLE, EXECUTING, FAILED, QUARANTINED, RETRY_PENDING, or otherwise retained for recovery. Terminal events are no longer eligible execution targets.

## 4. Event types

The closed initial event-type set is:

- `PERIPHERAL_READ`
- `PERIPHERAL_WRITE`
- `SERVICE`
- `HOUSEKEEPING`
- `RECOVERY_CONTROL`

`RECOVERY_CONTROL` is control-plane work generated by the recovery mechanism and is not automatically considered independent of the event it controls.

No additional event type is introduced unless a later experiment demonstrates that the existing types cannot express the workload without semantic distortion.

## 5. Producer, service, and consumer semantics

The baseline fields are interpreted as follows:

- **producer_id:** bounded source that creates/enqueues the event, such as an interrupt adapter, timer source, service, or host-control path.
- **service_id:** bounded logical service whose contract is being executed or advanced by the event.
- **consumer_id:** optional bounded execution endpoint/handler identity when it is materially different from the logical service.

`service_id` is the primary semantic ownership field for recovery and criticality. `consumer_id` is retained only when the implementation or experiment needs to distinguish dispatch endpoint from logical service.

This distinction avoids the earlier ambiguity in which producer, consumer, and service were treated as interchangeable concepts.

## 6. Peripheral association

An event has zero or one primary peripheral association in the reference model:

- `NONE`
- `I2C0`
- `SPI0`
- `UART0`/diagnostic equivalent

A future extension to multiple resources is out of scope for Gate A unless the selected workload genuinely requires it.

Peripheral association answers **which hardware interface the event touches**. It does not answer **which other events are dependent on it**.

The current platform direction remains STM32U575ZI / NUCLEO-U575ZI-Q. ST documents the STM32U575 as a Cortex-M33 device with an MPU and multiple I2C, SPI, USART/UART interfaces, supporting the platform direction used by this model. citeturn2search0turn2search12

## 7. Criticality

Criticality is a finite semantic class:

- `CRITICAL`
- `NORMAL`
- `DEFERABLE`

Criticality influences admission, preservation preference, and escalation decisions, but it never overrides dependency safety, ordering constraints, quarantine safety, or an explicitly unsafe execution condition.

Therefore:

`CRITICAL != automatically executable`

and

`DEFERABLE != automatically discardable`.

The policy must define what is safe before using criticality as a decision input.

## 8. Dependency taxonomy

### 8.1 INDEPENDENT

Event `Ej` is independent of `Ei` when `Ej` can execute correctly without any completion result, state transition, transaction outcome, or resource-validity guarantee established by `Ei`.

If `Ei` is quarantined, `Ej` remains eligible subject to all other constraints.

### 8.2 ORDERED

`Ei -> Ej` is an ordered dependency when `Ej` requires `Ei` to reach a declared acceptable predecessor state before execution.

The acceptable predecessor condition is not necessarily `COMPLETED`; it may be another explicitly defined terminal state if the service contract permits it.

Examples:

- configuration event before a dependent transfer;
- initialization before a read;
- commit/prepare sequence where later work requires the earlier stage.

If `Ei` is quarantined and has not reached the acceptable condition, `Ej` is blocked.

### 8.3 COUPLED/TRANSACTIONAL

Two events are coupled when they participate in the same logical transaction or share mutable state such that executing one while the other is invalid/quarantined could produce an incorrect partial transaction or inconsistent state.

Coupling is stronger than simple ordering. The model therefore does not reduce a coupled transaction to a precedence edge.

Examples:

- write followed by verification where both represent one logical transaction;
- paired operations whose shared transaction state must remain consistent;
- recovery-sensitive state transitions where partial execution is not valid.

A coupled event remains blocked unless the transaction contract explicitly permits the proposed transition.

## 9. Dependency representation

The semantic model uses a **bounded explicit dependency relation** rather than inferring dependencies from peripheral identity.

For each event, the reference representation is conceptually:

```text
DependencyEntry {
    referenced_event_ref
    dependency_kind      // ORDERED or COUPLED
    acceptable_condition // for ORDERED dependencies
}
```

`INDEPENDENT` requires no dependency entry.

The implementation uses a fixed maximum number `DMAX` of dependency entries per event. No event may declare more than `DMAX` incoming dependency references. This gives a statically computable worst-case bound:

`DependencyStorage <= ActiveEventSlots * DMAX * sizeof(DependencyEntry)`

A fixed entry array is preferred to a dynamic graph because it is inspectable, deterministic, and directly supports worst-case RAM accounting.

The exact packed C representation is deferred until implementation and Gate E footprint accounting. Gate A freezes the semantics, not the byte-level packing.

## 10. Dependency evaluation rule

Before dispatching `Ej`, the scheduler evaluates every declared dependency:

1. `INDEPENDENT` — no predecessor condition is required.
2. `ORDERED` — all referenced predecessors must satisfy their declared acceptable condition.
3. `COUPLED/TRANSACTIONAL` — the transaction/state contract must declare the event safe to execute; otherwise it remains blocked.

A dependency is evaluated against the referenced event's semantic state, not merely its presence or absence from the queue.

Therefore:

`not fault-associated != independent`

and

`not currently quarantined != safe to execute`.

## 11. Ordering semantics

The reference queue has FIFO **admission order**: events are inserted into a bounded queue in insertion order.

Execution, however, is governed by an eligibility predicate. FIFO position alone does not force an independent event to wait behind a quarantined event.

For ordered events:

`Ei ≺ Ej => Exec(Ei) precedes Exec(Ej)`

unless a later, explicit recovery transition reclassifies the relationship or releases `Ej` under a valid service contract.

For independent events, a quarantined predecessor does not by itself prevent execution.

This produces a deliberate distinction:

`queue order != universal execution order`.

The dispatcher may scan/select an eligible event according to the fixed scheduling rule defined in the implementation. That scheduling rule must itself be deterministic and documented before experiments.

## 12. Event lifecycle

The event lifecycle is refined to avoid ambiguous transitions in the baseline document.

```text
ADMITTED
   |
   v
QUEUED
   |
   | eligibility predicate satisfied
   v
ELIGIBLE
   |
   v
EXECUTING
   | \
   |  \
   |   +----> FAILED
   |             |
   |             +----> QUARANTINED
   |                         |
   |                         +----> RETRY_PENDING -> EXECUTING
   |                         |
   |                         +----> RELEASED -> ELIGIBLE
   |                         |
   |                         +----> DISCARDED [terminal]
   |                         |
   |                         +----> ESCALATED [terminal]
   |
   +----> COMPLETED [terminal]
```

Additional rules:

- `ADMITTED` means the event has been accepted into a fixed event slot; it is not yet executable.
- `QUEUED` means represented in the normal bounded work queue.
- `ELIGIBLE` means all currently evaluated execution constraints are satisfied.
- `EXECUTING` is the run-to-completion execution interval for the event handler in the cooperative reference model.
- `FAILED` records an execution failure before the recovery manager decides the next action.
- `QUARANTINED` means execution is prohibited until an explicit permitted transition.
- `RETRY_PENDING` is a recovery scheduling state, not a successful release.
- `RELEASED` is a transition outcome that returns an event to eligibility evaluation; it is not a terminal lifecycle state.
- `COMPLETED`, `DISCARDED`, and `ESCALATED` are terminal event outcomes.

No state transition may silently remove an event from all bounded representation.

## 13. Fault association boundary

Gate A does not freeze the fault taxonomy; Gate B does that. Gate A does freeze the identity semantics needed by Gate B.

The association confidence levels are:

1. `EXACT_EVENT_TRANSACTION` — fault is defensibly linked to an event/transaction reference.
2. `SERVICE_ONLY` — event-level association is unavailable but service-level association is defensible.
3. `PERIPHERAL_ONLY` — only peripheral-level association is defensible.
4. `UNKNOWN_AMBIGUOUS` — no sufficiently defensible association.

Association precision may not be inferred merely because a fault and an event share a peripheral.

The quarantine scope must never be more specific than the evidence supports.

Thus:

`association precision <= evidence precision`.

When association is ambiguous, the recovery policy may choose conservative service/peripheral containment in a later gate, but it may not falsely label a specific event as the fault source.

## 14. Quarantine semantics

Quarantine is an **execution prohibition plus retained representation**.

For event `Ei`:

`state(Ei) = QUARANTINED => Exec(Ei) is forbidden`

until a permitted transition occurs.

Quarantine is therefore not:

- deletion;
- implicit queue removal;
- global queue flush;
- proof that all events on the same peripheral are unsafe.

The recovery manager must retain enough bounded metadata to identify the quarantined event and evaluate its release/retry/discard/escalation transition.

## 15. Queue and quarantine storage model

The reference architecture uses two fixed bounded resource classes:

- `QMAX` normal event-queue slots;
- `XMAX` quarantine/recovery-retention slots.

A conservative initial engineering configuration for host-model experiments is:

- `QMAX = 16`
- `XMAX = 4`
- `DMAX = 4`

These are **provisional capacity parameters**, not claims about the final workload. Gate E must verify that the workload can exercise the mechanism without accidental capacity artefacts and must report the chosen capacities explicitly.

The active event domain is therefore bounded by:

`ACTIVE_MAX <= QMAX + XMAX`.

No dynamic expansion is permitted.

A quarantined event consumes one recovery-retention slot if it cannot remain represented in a normal queue slot without violating the queue implementation's invariants. The implementation must choose one concrete storage strategy before Gate E so that double-counting or hidden storage cannot occur.

## 16. Full-queue behavior

Full-queue behavior is part of correctness, not merely an implementation detail.

The deterministic admission rule is:

1. If a free normal queue slot exists, admit the event.
2. If the normal queue is full but the event is eligible for a predeclared reserved critical-admission path, admit it only within the separately bounded reservation.
3. Otherwise reject/defer the new event according to its declared producer contract and record the overflow outcome.
4. A critical event that cannot be represented without violating a declared safety requirement triggers the later escalation path; it is never silently dropped.

The reference mechanism must not reclaim a quarantined event simply because the queue is full. Any discard/release decision must follow its explicit event lifecycle and recovery semantics.

Gate E must determine whether a reserved critical slot is actually required by the experimental workload. If not required, the simpler all-capacity-bounded rule may be used.

## 17. Preservation correctness

For a fault-associated event `Ei`, define `U(Ei)` as the set of events that are valid, not fault-associated, and semantically independent of `Ei` under the declared dependency/state model.

An event `Ej` is **preserved** only if:

1. `Ej` executes;
2. its service/transaction verification succeeds;
3. no dependency or ordering rule is violated;
4. no invalid shared state is bypassed;
5. the execution is not later invalidated by the fault episode.

The preservation rate is:

`PreservationRate(Ei) = |Preserved(U(Ei))| / |U(Ei)|`

This metric is intentionally stricter than queue retention.

For events that are not independent, their non-execution is not counted as a preservation failure if blocking is required by dependency safety.

## 18. Quarantine correctness

Define:

`QuarantineViolation = count of executions of events whose state was QUARANTINED and for which no permitted release/reclassification transition existed before execution.`

Required target:

`QuarantineViolation = 0`.

Any non-zero result is a correctness failure, not a performance trade-off.

## 19. Dependency-safety predicate

An event is dispatchable only if:

```text
Dispatchable(Ej) =
    Represented(Ej)
    AND State(Ej) == ELIGIBLE
    AND AssociationAllowsExecution(Ej)
    AND AllOrderedDependenciesSatisfied(Ej)
    AND AllCoupledContractsSatisfied(Ej)
    AND SharedStateValid(Ej)
    AND ActiveRecoveryConstraintsAllow(Ej)
```

This predicate makes explicit why a simple queue scan that only checks `state != QUARANTINED` is insufficient.

## 20. Preservation vs. collateral blocking

The mechanism must distinguish three outcomes for an event that is not itself fault-associated:

- **PRESERVED:** safely executed and verified.
- **CORRECTLY_BLOCKED:** not executed because an explicit dependency/order/shared-state rule required blocking.
- **INCORRECTLY_BLOCKED/LOST:** not executed despite being valid and independent under the declared model.

This distinction prevents the evaluation from falsely rewarding aggressive blocking as "safe preservation."

## 21. Acceptance/rejection of the original baseline

### Accepted

The following baseline assumptions remain valid:

- bounded event identity;
- separate transaction identity where needed;
- finite event types;
- producer/service/peripheral metadata;
- finite criticality classes;
- independence vs ordered vs coupled/transactional distinction;
- explicit dependency relation;
- FIFO admission with constrained execution ordering;
- explicit lifecycle states;
- conservative fault association;
- quarantine as retained non-executable state;
- selective preservation rather than global flushing;
- bounded queue/quarantine storage;
- preservation and quarantine correctness metrics.

### Refined

The following baseline assumptions required clarification:

1. **Event identity** — `event_id` alone was insufficiently precise for slot reuse; the final semantic identity is `EventRef = {slot_id, generation}`.
2. **Consumer/service distinction** — service ownership is primary; consumer identity is retained only when it has independent semantic value.
3. **Dependency representation** — a generic "dependency mask or bounded reference set" is replaced by an explicit bounded relation with a fixed maximum entry count.
4. **Ordering** — FIFO queue order is separated from the execution eligibility predicate.
5. **Lifecycle** — `RELEASED` is a transition outcome, not a persistent state; `ADMITTED` and `RETRY_PENDING` clarify representation and recovery scheduling.
6. **Quarantine storage** — the final architecture must explicitly account for whether a quarantined event occupies a normal queue slot or a quarantine slot; hidden duplication is prohibited.
7. **Full queue** — overflow behavior is an explicit correctness condition rather than an unresolved implementation detail.
8. **Preservation** — preservation means correct verified execution, not mere retention in storage.

### Rejected

The following interpretations are explicitly rejected:

- same peripheral implies dependency;
- non-fault-associated implies safe to execute;
- criticality overrides dependency/safety;
- quarantine means delete;
- quarantine means global queue flush;
- FIFO position alone defines execution order;
- ambiguous association may be silently narrowed to an event;
- a blocked dependent event is automatically a lost event;
- queue occupancy alone proves service preservation.

## 22. Gate A unresolved questions carried forward

Gate A is complete despite the following intentionally deferred questions:

1. Exact fault classes and fault-injection semantics — Gate B.
2. Exact context/history variables and recovery-action rules — Gate C.
3. Formal transition properties and verification method — Gate D.
4. Final workload, queue-capacity stress, repetitions, and experimental metrics — Gate E.
5. Exact byte-level C struct packing — implementation stage after Gate E.
6. Whether the selected physical peripheral creates multi-resource dependencies that require a later bounded extension.

These are not failures of Gate A; they are deliberately outside its acceptance boundary.

## 23. Gate A acceptance decision

**ACCEPTED.**

Gate A is considered complete because the model now provides:

- an unambiguous bounded event identity;
- a closed initial event vocabulary;
- explicit producer/service semantics;
- explicit peripheral and criticality semantics;
- a non-peripheral-based dependency taxonomy;
- a bounded dependency representation;
- separate admission and execution-order semantics;
- an explicit event lifecycle;
- a bounded fault-association boundary;
- retained quarantine semantics;
- bounded queue/quarantine assumptions;
- deterministic full-queue rules;
- preservation and quarantine correctness definitions;
- explicit acceptance/rejection of the prior baseline assumptions.

The next gate is **Gate B — Fault Model + Fault Association**. No large-scale firmware implementation begins before Gates B–E are sufficiently specified.
